> 说明：本文为设计阶段的 AI 推理规格，向量检索部分按 pgvector 设计。V1 实际实现为 embedding 存 jsonb、应用层余弦相似度检索（切块量级为百级）；数据量变大后再迁移到 pgvector。

# AI推理规格文档
本文档为MVP阶段文档，用于指导 MVP 版本 AI 推理逻辑的开发实现。
MVP 版本聚焦核心业务闭环，暂不包含非必要的 AI 扩展能力，后续迭代再补充完善。

项目名称：Collaborative Candidate Verification Web App
版本：V1.0.0
最后更新：2026.9.21
作者：Nirvana

1. 模型选型（Model Selection）
### 1.1 最终选型
MVP 阶段主要使用 DeepSeek 作为 LLM 模型，暂不针对不同 Call 拆分不同模型。
### 1.2 Temperature
Temperature 暂未定，根据不同任务类型进行调整。
- 结构化提取、事实判断等需要稳定输出的任务使用较低 Temperature。
- 验证问题生成、对话调整等需要一定生成性的任务可适当提高 Temperature。
- 具体数值在开发及实际测试阶段根据输出稳定性进行确定。

### 1.3 已知局限性
MVP 阶段暂不建立复杂的多模型路由机制。模型效果、响应速度和实际成本在开发测试后再根据真实
数据进行调整。

2. 任务定义（Task Definition）
### 2.1 AI 总体任务
系统通过多个 LLM Call 对候选人的简历、岗位要求、企业知识、面试记录及用户选择进行逐阶段分
析，形成：

简历理解 → 验证方向 → 验证问题 → 面试证据分析 → 剩余验证项 → 单轮总结 → 多轮总总结
其中用户在关键节点参与选择和调整，AI 不直接替代用户完成验证方向和问题选择。
### 2.2 总体 Workflow
#### 2.2.1 阶段 A：简历理解
 简历 + JD + 企业知识
 ↓
 拆解/理解简历，提取经历与关键声明
 ↓
 结构化经历 + 关键声明 + 企业 RAG 资料 + 岗位原始要求
#### 2.2.2 阶段 B：验证方向形成
 结构化经历 + 关键声明 + 企业 RAG 资料 + 岗位原始要求
 ↓
 识别疑点并生成验证方向
 ↓
 用户选择验证方向
 ↓
 理解用户选择的验证方向
#### 2.2.3 阶段 C：验证问题形成
 用户选择的验证方向
 ↓
 提取需要进一步验证的事实维度，并生成检索 Query
 ↓
 结合候选人结构化经历、岗位要求、企业 RAG 结果、验证方向及事实维度
 ↓
 判断已有证据 / 信息缺口
 ↓
 生成验证问题池
 ↓
 用户确认 / 调整

#### 2.2.4 阶段 D：面试验证
  面试记录 + 已确认验证问题 + 历史验证材料
  ↓
  提取面试事实、声明和证据，并关联原文位置
  ↓
  识别剩余疑点并判断当前验证状态
  ↓
  剩余待验证项 / 验证方向
  ↓
  用户选择验证方向
  ↓
  生成下一轮验证问题
上述验证机制可根据面试轮次持续迭代；每一轮均基于上一轮已经获得的验证材料继续判断，而不是
重新从候选人简历开始分析。
#### 2.2.5 阶段 E：单轮结束
 本轮面试逐字稿 + 面试官记录 + 验证问题 + 面试官反馈 + 本轮分析结果
 ↓
 结构化聚合并生成单轮面试总结
 ↓
 单轮面试总结
#### 2.2.6 阶段 F：全部面试轮次结束
 全部已经归档确认的单轮面试总结
 ↓
 跨轮结构化聚合
 ↓
 结合岗位信息及企业知识进行综合判断
 ↓
 候选人面试总总结

3. 推理管线（Inference Pipeline）
### 3.1 Call 1：简历解析
- 输入：
  简历 + JD
- 处理：
  拆解/理解简历，提取经历与关键声明，并生成检索 Query。
- 输出：
  结构化经历 + 关键声明 + Query。

### 3.2 Call 2：验证方向识别
- 输入：
  结构化经历 + 关键声明 + 企业 RAG 资料 + JD
- 处理：
  结合候选人关键声明、JD 和企业知识识别疑点并生成验证方向。
- 输出：
  验证方向。

### 3.3 Call 3：用户选择验证方向理解
- 输入：
  Call 1 结构化结果 + 用户选择的验证方向
- 处理：
  拆解/理解用户选择的验证方向， ，并生成检索 Query。
- 输出：
  待验证事实维度 + Query。

### 3.4 Call 4：验证问题生成
- 输入：
  Call 1 结构化结果 + 岗位要求 + 企业 RAG 结果 + 用户选择的验证方向 + 事实维度框架。
- 处理：
  判断需要进一步验证的事实维度、已有证据及信息缺口。

- 输出：
 具体验证问题。

### 3.5 Call 5：面试文件解析
- 输入：
  采用的验证问题 + 面试逐字稿 + 面试观察评价/记录。
- 处理：
  拆解/理解面试逐字稿及面试观察评价/记录，提取声明、事实和证据；将已确定事实与原文位置关
  联，生成标注文件，并生成检索 Query。
- 输出：
  结构化结果 + Query。

### 3.6 Call 6：验证方向生成
- 输入：
  Call 5 结构化结果 + 确认的验证问题 + 逐字稿标注文件 + 企业 RAG 结果 + 岗位要求。
- 处理：
  识别剩余疑点并判断当前验证状态。
- 输出：
  验证分析结果 + 剩余验证方向。

### 3.7 Call 7：用户选择的验证方向解析
- 输入：
  Call 5 面试证据结构化结果 + Call 6 验证分析结果 + 用户选择的验证方向。
- 处理：
  拆解/理解用户选择的验证方向，明确该验证方向对应的判断标准，并生成检索 Query。
- 输出：
  两套素材框架 + Query。

### 3.8 Call 8：验证问题生成
- 输入：
 Call 5 结构化结果 + 两套素材框架 + 岗位要求 + 企业 RAG + 用户选择的验证方向。

- 处理：
  判断基于素材框架需要进一步验证的问题，以及已有证据 / 信息缺口。
- 输出：
  具体验证问题。

### 3.9 Call 9：用户对话解析
- 输入：
  逐字稿疑点标注文件 + 面试观察评价/记录 + 候选人简历 + 岗位要求 + Call 8 验证问题 + 完整本轮对
  话记录。
- 处理：
  拆分和理解用户对话记录，提取用户对问题池的调整指令，并生成检索 Query。
- 输出：
  用户对话指令 + Query。

### 3.10 Call 10：新验证问题生成
- 输入：
  Call 8 验证问题 + Call 9 用户对话指令 + 岗位要求 + 企业 RAG 结果。
- 处理：
  基于已经锁定的待验证事实及尚未验证要求，对问题池中已有题目进行改写、新增或删减。
- 输出：
  新的验证问题池。

### 3.11 Call 11：单轮面试结构化聚合
- 输入：
  本轮面试逐字稿 + 面试观察记录 + 本轮待验证问题 + 面试反馈 + 疑点标注文件。
- 处理：
  对本轮面试全部上下文材料进行结构化聚合，并生成检索 Query。
- 输出：
  单轮面试事实 / 能力 / 验证结果。

### 3.12 Call 12：单轮面试总结生成

- 输入：
  Call 11 结构化结果 + 企业 RAG 结果 + 用户选定验证问题 + 单轮面试总结表模板。
- 处理：
  提取本轮事实信息、能力维度及业务属性，并按照单轮面试总结表模板生成总结内容。
- 输出：
  单轮面试总结表结构化 JSON + 单轮面试总结表。

### 3.13 Call 13：候选人多轮面试结构化聚合
- 输入：
  全部已经归档确认的单轮面试总结表（包含各轮当时快照的面试反馈）+ 岗位信息 + 各轮标注文
  件。
- 处理：
  对已经确认的多轮单轮总结进行跨轮结构化聚合，并生成总总结所需的检索 Query。
- 输出：
  候选人的多轮面试结构化聚合结果 + Query。

### 3.14 Call 14：候选人总总结生成
- 输入：
  Call 13 多轮结构化聚合结果 + 岗位信息 + 企业 RAG 结果 + 候选人总总结表模板。
- 处理：
  根据岗位要求及企业标准，对候选人的多轮面试结果进行综合判断和总结。
- 输出：
  候选人面试总总结表结构化 JSON + 候选人面试总总结表。

4. 检索策略（Retrieval Policy）
### 4.1 Query 生成
Query 由前序 LLM Call 根据当前任务生成，用于从企业知识库中检索与当前分析任务相关的企业资
料。
主要检索链路如下：
- Call 1 → Call 2
   Query： 搜索企业对岗位的职责/岗位要求。

   ↓
   将 Query 转换为向量，在 pgvector 中检索相关企业资料。
   ↓
   返回相关企业资料，作为 Call 2 的上下文。
- Call 3 → Call 4
   Query： 搜索企业对事实维度的定义。
   ↓
   pgvector 检索企业相关资料。
   ↓
   返回相关企业资料，作为 Call 4 的上下文。
- Call 5 → Call 6
   Query： 搜索尚未验证的岗位 / 公司要求。
   ↓
   pgvector 检索企业相关资料。
   ↓
   返回相关企业资料，作为 Call 6 的上下文。
- Call 7 → Call 8
   Query： 去企业知识库寻找相关标准 / 业务背景。
   ↓
   pgvector 检索企业相关资料。
   ↓
   返回相关企业资料，作为 Call 8 的上下文。
- Call 9 → Call 10
   Query： 搜索企业对岗位职责 / 岗位要求。
   ↓
   pgvector 检索企业相关资料。
   ↓
   返回相关企业资料，作为 Call 10 的上下文。
- Call 11 → Call 12
   Query： 搜索企业用于单轮面试总结的相关标准 / 业务知识。
   ↓
   pgvector 检索企业相关资料。
   ↓
   返回相关企业资料，作为 Call 12 的上下文。
单轮面试总结表模板属于系统预定义模板，不通过 RAG 检索。
- Call 13 → Call 14

  Query： 根据候选人总总结所需的企业标准 / 业务知识生成检索需求。
  ↓
  pgvector 检索企业相关资料。
  ↓
  返回相关企业资料，作为 Call 14 的上下文。
候选人总总结表模板属于系统预定义模板，不通过 RAG 检索。
### 4.2 RAG 检索链路
企业资料首先通过知识库建立流程进行处理：
  代码块
  1 企业资料上传
  2   ↓
  3   Supabase Storage
  4   ↓
  5   文件解析
  6   ↓
  7   文本切分 Chunk
  8   ↓
  9   Embedding
 10   ↓
 11   Supabase pgvector

AI Workflow 运行过程中，根据当前 Call 生成的 Query 进行向量检索，并将召回结果作为后续 LLM
Call 的上下文。
### 4.3 RAG 无有效召回结果
有以下两种：
1. pgvector 调用异常：调用异常按照 Retry 策略处理。
2. pgvector 调用正常但无有效召回结果：调用正常但没有有效企业资料时，不阻塞当前 Workflow，
   记录企业知识依据不足，并复用已有 JD / 项目数据继续后续分析。

5. 输出契约（Structured Output）
### 5.1 基本规则
需要供后续 Workflow、数据库或前端继续使用的 LLM 输出统一采用结构化 JSON。

Structured Output 用于固定 AI 输出的数据结构，保证下游 Workflow 能稳定读取和处理结果，避免
自由文本格式漂移造成解析异常。
### 5.2 各 Call 输出用途
- Call 1、3、5、7、9、11、13： 输出结构化中间结果，供后续检索及 LLM Call 使用。
- Call 2、4、6、8、10、12、14： 输出业务分析结果，用于快照保存、前端展示及后续业务流程。
结构化结果经过 Schema 校验后再进入后续 Workflow 或持久化流程。
### 5.3 校验规则
- 字段必须符合预定义 Schema。
- 字段类型必须符合定义。
- 必填字段缺失或结构不符合要求时，视为 Structured Output 校验失败。
- 可重试的结构化输出错误进入 Retry 流程。
- 重试仍失败则当前 AI Task 进入 failed。

6. 系统准则（System Rules）
### 6.1 推理原则
1. AI 仅基于当前 Workflow 提供的候选人资料、岗位要求、企业知识及用户输入进行分析。
2. 已有结构化结果优先作为后续 Call 输入，避免重复解析原始长文本。
3. 企业知识通过 RAG 提供业务标准、岗位要求及业务背景等上下文。
4. AI 负责分析、提取、判断和生成验证内容；验证方向及问题的关键选择保留用户参与。
5. 已确认的面试材料作为后续轮次的历史验证依据，不重新覆盖已经确认的结果。
### 6.2 负向约束
- 不得在缺乏输入证据时虚构候选人经历或面试事实。
- 不得将模型推测直接作为候选人已确认事实。
- 不得脱离岗位要求和企业知识生成与当前验证任务无关的问题。
- 不得输出不符合规定 Schema 的结构化结果。
- 不得因为 RAG 无有效召回结果而虚构企业标准或业务知识。

7. 上下文管理（Context Management）
### 7.1 上下文来源
AI 上下文主要来自：
- 前序 Call 的结构化结果；
- 候选人简历及面试材料；
- 岗位信息；
- 企业 RAG 结果；
- 当前验证问题；
- 用户选择的验证方向；
- 必要的历史验证材料；
- AI 对话调整中的必要历史消息。

### 7.2 上下文传递
优先传递前序 Call 已生成的结构化结果，不重复传递已经完成结构化处理的无关原始长文本。
不同 Call 根据当前任务需要组合必要上下文，不默认传递全部历史数据。
### 7.3 Token 控制
MVP 阶段不预设固定 Token 消耗值，主要通过以下方式控制：
- 复用前序 Call 的结构化结果；
- 减少重复传递原始文本；
- 控制输入上下文；
- 对过长的对话历史进行截断；
- 仅保留当前任务需要的历史内容。
AI 对话调整场景采用：当前用户消息
- 必要历史消息
- 当前项目 / 候选人 / 面试轮次上下文。

8. 失败处理（Retry / Timeout / Fallback）
### 8.1 Retry

Retry 仅用于临时性、具备恢复可能性的异常，目前设置最大重试次数：2 次。
- 重试等待：
    ◦ 第一次重试：等待 2s；
    ◦ 第二次重试：等待 5s。
- 可重试场景包括：
    ◦ LLM API 网络 / 服务异常；
    ◦ LLM 请求超时；
    ◦ Structured Output 校验失败；
    ◦ pgvector 可恢复调用异常。
Retry 期间 AI Task 前端仍显示 processing ，不向用户暴露独立的 retrying 状态。
### 8.2 Timeout
- 采用单 Call 超时 + 整体 Task 超时。
  ◦ 单 Call： 设计参考范围为 20–30s，最终数值在开发阶段根据实际响应确定。
  ◦ 整体 Task： 最大执行时间 120s。
达到整体 Task 超时后立即终止当前 Workflow，不再发起后续调用，并将 Task 标记为 failed 。
### 8.3 Fallback
RAG 检索正常但没有有效企业资料时：
  代码块
  1 生成 Query
  2    ↓
  3    pgvector   检索
  4    ↓
  5    无有效召回
  6    ↓
  7    记录“企业知识依据不足”
  8    ↓
  9    复用已有 JD / 项目数据
  10   ↓
  11   继续后续 LLM Call

如果输入本身无效、无法提取有效业务信息或达到整体 Task 超时等不可恢复情况，则不进行 Retry，
直接进入 failed 。

9. MVP 范围说明
本 AI 推理规格文档仅定义当前 MVP 所需的 AI 推理链路及其运行规则。
暂不在本版本展开：
- 多模型路由；
- 复杂 Agent 自主循环；
- Rerank 等额外检索层；
- 固定 Token 成本模型；
- 复杂 Prompt 版本管理；
- 完整模型评测体系；
- 大规模线上运营指标。
上述能力在后续迭代阶段根据实际运行数据和业务需求增加。
