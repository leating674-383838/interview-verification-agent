# 风险与待验证假设

> 摘自 [PRD](PRD.md) 第八部分。假设的验证状态如实标注，未验证的不当作结论。

## 8.1 产品假设列表（标注验证状态）
我们设计的这个产品机制，真的能产生预期效果吗？
1. AI可以候选人的简历信息生成有效的验证任务。
2. AI可以从岗位能力要求提取真正影响招聘判断的关键能力。
3. HM愿意在面试前使用验证任务。
4. HM认为验证任务能补充简历无法证明的信息。
5. 面试官之间的信息能有效承接，多轮验证衔接效果好。
6. birighthire产品的核心侧重是做候选人真实性是否欺诈和面试决策辅助。 metaview产品的核心侧
   重是对是否有合适岗位的候选人的抓取以及面试笔记辅助和决策辅助。 我的产品侧重于根据多轮跨
   轮次验证衔接对验证候选人的经历真实性验证和能力评估。 跨轮次服务于不同目的，所以差异化切
   口“跨轮次验证衔接”依然成立，与竞品的侧重不重叠。
## 8.2 技术风险
1. 不同岗位怎么设计？
2. 测评结果是否具有法律/合规风险？
3. 因为涉及大量上下文，是否能把控好分析程度而不会误判？
4. RAG检索结果是否准确？
   企业文件质量参差不齐时是否影响验证问题质量？
5. 多轮上下文累积后Agent是否能保持判断稳定，不出现前后矛盾？
  - 公司规模；
  - 项目复杂度；
  - 岗位级别；
  - 面试官标准；
  - 团队需求。

## 8.3 用户接受度风险
1. 用户是否愿意采用这个新的行为/流程/机制？
2. 面试官是否愿意在面试前额外花时间查看验证问题，还是觉得多此一举？
3. 企业是否愿意上传内部文件（职级标准、SOP、业务资料）到第三方系统？隐私顾虑是接受度风险吗？
